# VPS Route

Run official Claude Code in a separate local environment, with its HTTPS traffic
routed through your own VPS over SSH. If the connection fails, there is no direct fallback.

Linux only. Requires your own VPS and Claude account. Claude is downloaded during
setup, not bundled with the tool. Not affiliated with Anthropic.

[中文使用说明](docs/USAGE.zh-CN.md) · [First-time setup example](docs/FIRST_RUN.zh-CN.md)
· [Security](docs/SECURITY.md)

## Requirements

- Your computer: Linux, Python 3.10+ (including `/usr/bin/python3`), bubblewrap,
  OpenSSH, curl and Bash. Unprivileged network namespaces must work.
- Your VPS: Linux, `/usr/bin/python3` 3.10+, systemd, outbound HTTPS/DNS,
  SSH key login and Unix-socket forwarding. Non-root users need a working systemd user service.
- An SSH private key and a verified VPS host fingerprint.

On Ubuntu/Debian, install the client dependencies:

```bash
sudo apt-get install git gh python3 python3-venv pipx bubblewrap openssh-client \
  netcat-openbsd curl ca-certificates
```

## Install the tool

Clone the repository with an account that has access, then install:

If needed, sign in to GitHub first with `gh auth login`.

```bash
gh repo clone sidiangongyuan/vps-route
cd vps-route
pipx install .
pipx ensurepath
```

Open a new terminal if `vps-route` is not found. Alternatively, install in a
virtual environment; see the [setup guide](docs/FIRST_RUN.zh-CN.md).
The package is not published to PyPI.

## First-time setup

```bash
vps-route init
vps-route setup-vps --apply
vps-route doctor --connect
vps-route install
vps-route auth login
vps-route auth status --text
```

`init` asks for your VPS address, SSH user/port, key and known-hosts paths,
and the private service path on the VPS. No fixed exit IP is required.
See the [complete example](docs/FIRST_RUN.zh-CN.md) for what each field means.
Skip `setup-vps` if your VPS already has a compatible service.

For login, open the official URL printed in the terminal using a browser routed
through the same intended exit. Paste the returned one-time code into that same
waiting terminal. The tool does not route your browser or provide a remote desktop.

Repeated `init` reuses your environment without clearing login or history.
Repeated `install` skips an existing executable installation entry; use `update`
to upgrade Claude. Conflicting configs or invalid entries are not overwritten.

## Use a setup token

After `init` and `install`, you can import a long-lived token generated by
official `claude setup-token` instead of choosing browser login:

```bash
vps-route auth import-token
vps-route auth status --text
vps-route run
```

Paste the token at the hidden prompt. It is stored with permissions `0600` in
`~/.local/share/claude-launcher/profiles/<profile>/.launcher-auth/setup-token`,
inside a `0700` directory. Only this profile's new Claude sessions receive it.
Existing sessions, saved browser login, history and VPS settings stay unchanged.
An imported token takes priority over saved browser credentials; malformed or
unsafe storage stops startup. Explicit credentials/providers in Claude settings
still follow the official authentication precedence.
The import and local status check do not test server-side validity. Claude reports
expired/revoked credentials when it makes a request.

Use `auth import-token --replace` to explicitly replace a stored token.
To return to browser login, preview `vps-route auth remove-token`, then run
`vps-route auth remove-token --apply` and `vps-route auth login`.
Removal affects this local copy; upstream revocation is separate.
Profile reset archives the token with the old profile. Uninstall follows the
existing profile/backup retention options.

Treat the token as a long-lived password. The import command keeps it out of
arguments, shell history and tool logs. Claude and its child processes receive
it in their environment; the same OS user or an administrator can access it.
Importing does not clear history or establish a new account identity.
Token permissions and supported features follow
[the official authentication documentation](https://code.claude.com/docs/en/authentication#generate-a-long-lived-token).
The token does not configure networking; the same VPS isolation remains required.

## Tab completion

Enable once in the current shell:

```bash
# Zsh (including macOS):
source <(vps-route completion zsh)

# Bash:
source <(vps-route completion bash)
```

Add the matching `source` line to your shell startup file (`~/.zshrc` for Zsh,
`~/.bashrc` for interactive Bash; macOS login Bash may use `~/.bash_profile`).
Then type `vps-route au<Tab>` or `vps-route auth imp<Tab>`.
Completion covers command names, subcommands, options and path arguments.
It reads argument metadata only, with no config/account reads or VPS connections.
Bash completion uses Bash 3.2-compatible syntax; macOS runtime validation is
tracked separately on the experimental `macos-support` branch.

## Daily use

```bash
cd /path/to/your/project
vps-route run
```

The same command works in a VS Code Remote SSH terminal. Installing this tool
does not replace an existing `claude` command or configure the VS Code extension.

For Orca's local multi-agent control, start from an Orca-managed Linux terminal:

```bash
vps-route run --orca
```

This opt-in exposes the selected local Orca CLI and runtime socket, not its
account databases. It currently supports Orca's Linux remote Node CLI wrapper.
To enable it automatically for this profile's Orca-managed terminals and child
agents, run `vps-route config set orca_control true --apply`. Plain SSH terminals
without `ORCA_CLI_COMMAND` are unaffected; set it back to `false` to disable.
The Claude process keeps its isolated network and VPS route. Orca can also start
host-side terminals/agents, which are outside that network boundary; ensure every
new Claude agent uses your VPS Route launcher. See [Security](docs/SECURITY.md).

| Need | Command |
| --- | --- |
| Check the connection and exit | `vps-route doctor --connect` |
| Check login | `vps-route auth status --text` |
| Update Claude | `vps-route update` |
| Show Claude's version | `vps-route native-version` |
| Resume a conversation | `vps-route run -- --resume SESSION_ID` |
| Disable customizations for troubleshooting | `vps-route run --safe-mode` |
| See recent connection logs | `vps-route logs --tail 20` |

## What stays separate

Claude's installation, login and history live in:

```text
~/.local/share/claude-launcher/profiles/default/
```

Your existing Claude data is not moved or deleted. Normal runs support skills,
project `CLAUDE.md`, rules and automatic memory. Hooks, MCP, account connectors,
remote control and cloud skill sync are disabled.

Before launch, the tool checks HTTPS connectivity through your VPS. During `run`,
Claude displays request errors and handles its own retries. The tool keeps your
session open and silently reconnects lost SSH connections through the same
configured VPS, without a direct fallback. There are no periodic HTTPS probes or
extra connection-status messages during daily use. SSH identity/authentication
failures still show a notice when automatic reconnect cannot continue.
Once connectivity returns, retry interrupted requests if needed. Login, install
and update commands still stop on route failure.
A changed exit IP does not stop Claude.
`doctor --connect` shows the observed exit IP for information only; a failed IP
lookup does not fail an otherwise successful connectivity check.
Its `diagnosis` section explains local setup failures, SSH authentication or host
identity errors, failure to reach the VPS, and failure after reaching its proxy.
SSH timeouts are reported as VPS-or-network-path failures: they cannot identify
which side failed, or diagnose an upstream that was never reached. No particular
upstream provider or fixed exit IP is required.
Only `doctor --connect` additionally tests the configured local network path against
the HTTPS targets in `connectivity_urls`, concurrently within the configured timeout.
With `ssh_http_proxy`, these control requests use that proxy exclusively; otherwise
they use the system network. They carry no Claude credentials and follow no redirects.
Failed control probes still allow the VPS checks to proceed. The report distinguishes
failed local controls from a VPS-specific SSH failure, while leaving uncertain causes
explicit. Normal startup and running sessions keep their existing checks and retry behavior.
Browsers and unrelated applications are not covered. See [Security](docs/SECURITY.md).

## Update or uninstall the tool

Close active VPS Route sessions, then update from your checkout:

```bash
git pull --ff-only
pipx reinstall vps-route
```

To uninstall, review the deletion list first:

```bash
vps-route uninstall --dry-run
vps-route uninstall
```

Uninstall permanently removes local tool data, including login, history and
historical backups. To keep your Claude data, use `--keep-profiles --keep-backups`.
It does not remove anything on the VPS.
